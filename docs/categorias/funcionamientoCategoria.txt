 # Funcionalidad: Gestión y Análisis de Categorías

**Versión:** 2.0
**Fecha:** 2025-05-23

Este documento detalla la arquitectura técnica y el flujo de datos de la funcionalidad de categorización de movimientos, incluyendo la asignación automática de categorías para pagos de deudas.

---

## 1. Arquitectura y Decisiones de Diseño

La gestión de categorías se diseñó como un sistema centralizado en el backend para garantizar la consistencia y flexibilidad, evitando tener valores fijos (hardcodeados) en el frontend.

### 1.1. Backend como Única Fuente de Verdad (Single Source of Truth)

*   **Decisión Técnica**: Se creó una entidad `Categoria` en la base de datos del backend, servida a través de un endpoint `GET /api/categorias`. Esto permite añadir, eliminar o modificar categorías en el futuro sin necesidad de actualizar y redistribuir la aplicación móvil.
*   **Población Inicial de Datos**: Para asegurar que la aplicación tenga un conjunto de categorías funcionales desde el primer arranque, se implementó un `DataLoader` (`CommandLineRunner` de Spring). Esta clase inserta una lista predefinida de categorías (Comida, Transporte, Sueldo, etc.) solo si la tabla de categorías está vacía, evitando la duplicación de datos en reinicios posteriores.

### 1.2. Relación entre `Movimiento` y `Categoria`

*   **Decisión Técnica**: Se estableció una relación `@ManyToOne` desde `Movimiento` hacia `Categoria`. Esto significa que cada movimiento puede tener una (y solo una) categoría. Se eligió una carga `EAGER` para la categoría en la entidad `Movimiento`, ya que es información pequeña y frecuentemente necesaria, simplificando las consultas.

### 1.3. Categorización Automática de Deudas

*   **Decisión de Diseño**: Para que los pagos de deudas se reflejen correctamente en los análisis de gastos, se determinó que debían ser tratados como cualquier otro gasto, es decir, debían tener una categoría.
*   **Implementación**: En lugar de dejar esta asignación al usuario, se automatizó en el backend para eliminar errores y mejorar la experiencia. En el `DeudaService`, dentro del método `registrarPago`, el sistema ahora realiza los siguientes pasos:
    1.  Busca la categoría con el nombre "Deudas" usando un nuevo método `findByNombre` en el `CategoriaRepository`.
    2.  Asigna esta categoría al `Movimiento` de tipo `PAGO_DEUDA` antes de guardarlo.
*   **Resultado**: Cualquier pago de deuda se clasifica automáticamente, integrándose sin problemas en el sistema de análisis.

## 2. Flujo de Datos Completo

1.  **Carga Inicial**: Al iniciar el `DashboardScreen`, el `DashboardViewModel` dispara dos llamadas en paralelo:
    *   `GET /api/categorias` para obtener la lista de todas las categorías disponibles.
    *   `GET /api/movimientos/usuario/{rut}?limit=10` y `GET /api/saldos/{rut}` para los datos del dashboard.

2.  **Registro de Gasto/Ingreso Manual**:
    *   El usuario abre el diálogo `AddTransactionDialog`.
    *   El componente `CategorySelector` se renderiza, mostrando las categorías obtenidas en el paso 1.
    *   Al confirmar, la app realiza un `POST /api/movimientos` enviando los detalles del movimiento junto con el `categoriaId` seleccionado.

3.  **Registro de Pago de Deuda**:
    *   El usuario realiza un pago desde `DeudasScreen`.
    *   La app llama a `POST /api/deudas/{deudaId}/pagar`.
    *   El **backend** (`DeudaService`) intercepta esta acción, crea el movimiento de gasto (`PAGO_DEUDA`), busca la categoría "Deudas" y se la asigna internamente antes de guardar.

4.  **Visualización en Historial y Análisis**:
    *   Cuando se pide la lista de movimientos (ej. en `DashboardScreen` o `AnalysisScreen`), el backend (a través de `MovimientoService` y `MovimientoResponseDTO`) ahora incluye el objeto `CategoriaDTO` completo en cada movimiento que tenga una asignada.
    *   En `AnalysisScreen`, la lógica de la UI filtra la lista de movimientos para incluir tanto los de tipo `GASTO_GENERAL` como `PAGO_DEUDA`, y los agrupa por `categoria.nombre` para construir el gráfico y el resumen.

## 3. Implementación Detallada (Clases Clave)

### Backend (`saveup`)

*   **`DataLoader.java`**: Inicializa la base de datos con categorías, incluyendo "Deudas".
*   **`Categoria.java` (Entidad)**: Define la tabla `CATEGORIA`.
*   **`CategoriaRepository.java`**: Incluye `findByNombre(String nombre)` para búsquedas específicas.
*   **`Movimiento.java` (Entidad)**: Actualizada con la relación `@ManyToOne` a `Categoria`.
*   **`DeudaService.java`**: Lógica clave en `registrarPago` para encontrar y asignar la categoría "Deudas".
*   **`MovimientoService.java`**: Lógica clave en `convertirAEntidadResponseDTO` para poblar el `CategoriaDTO` en la respuesta.
*   **DTOs (`MovimientoResponseDTO`, `MovimientoRegistroDTO`)**: Modificados para enviar y recibir el ID de la categoría y para incluir el objeto categoría en las respuestas.

### Frontend (`LITEfront`)

*   **`DashboardViewModel.kt`**: Orquesta la carga de categorías y el registro de nuevos movimientos.
*   **`AnalysisViewModel.kt`**: Carga el historial completo de movimientos para que la UI los procese.
*   **`DashboardScreen.kt`**: Muestra el `CategorySelector` en el diálogo de transacción y el `TransactionItem` ahora renderiza el nombre de la categoría.
*   **`AnalysisScreen.kt`**: Contiene la lógica de `remember(movimientos)` que filtra por `GASTO_GENERAL` y `PAGO_DEUDA` para agregar los datos para el `PieChartComponent`.
*   **`CategorySelector.kt`**: Componente de UI reutilizable para la selección de categorías.

## 4. Clasificación por Tipo de Presupuesto (Necesidad vs Deseo)

**Fecha de Actualización: 2025-12-30**

Para dar soporte a la funcionalidad de "Presupuesto 50/30/20", se introdujo una clasificación semántica adicional a las categorías.

### 4.1. Enum `TipoPresupuesto`
Se añadió el enum `TipoPresupuesto` con los siguientes valores:
*   `NECESIDAD`: Gastos esenciales (Comida, Transporte, Cuentas).
*   `DESEO`: Gastos prescindibles u ocio (Cine, Ropa, Salidas).
*   `AHORRO`: Reservado para metas de ahorro (aunque el ahorro se maneja principalmente vía `MetaAhorro`).
*   `OTROS`: Categorías por defecto o sin clasificación específica.

### 4.2. Impacto en la Entidad `Categoria`
*   Se agregó la columna `TIPO_PRESUPUESTO` en la BD.
*   El `DataLoader` asigna estos tipos por defecto (ej. "Comida" -> `NECESIDAD`).
*   Esto permite calcular en tiempo real (en el endpoint `/api/presupuestos/ejecucion`) cuánto del presupuesto asignado a "Necesidades" se ha consumido basándose en las categorías de los movimientos registrados.
