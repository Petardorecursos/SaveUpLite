## Arquitectura y Flujo de Datos del Nuevo Backend

El nuevo backend separa claramente las responsabilidades en diferentes capas y componentes para evitar los errores del pasado.

1.  **DTO (Data Transfer Object):** Clases como `UsuarioRegistroDTO` son la única puerta de entrada de datos. Son responsables de recibir los JSON del frontend y **validar** que los datos (formato de RUT, longitud de contraseña, etc.) sean correctos **antes** de que cualquier lógica de negocio se ejecute.

2.  **Controller (`@RestController`):** Es el punto de entrada de las peticiones HTTP.
    *   Recibe el DTO del frontend.
    *   Usa la anotación `@Valid` para activar las validaciones del DTO. Si un dato es inválido, el controlador rechaza la petición automáticamente con un error `HTTP 400 Bad Request`.
    *   Llama al `Service` correspondiente para ejecutar la lógica de negocio.
    *   Devuelve respuestas HTTP claras (`201 CREATED`, `409 CONFLICT`, etc.).

3.  **Service (`@Service`):** Es el cerebro de la aplicación.
    *   Contiene toda la lógica de negocio (registrar un usuario, iniciar sesión, etc.).
    *   Se comunica con el `Repository` para acceder a la base de datos.
    *   Realiza operaciones críticas de seguridad, como **codificar la contraseña** usando `PasswordEncoder`.

4.  **Repository (`@Repository`):** Es la capa de acceso a datos.
    *   Define métodos eficientes para interactuar con la base de datos (ej: `findByEmail`, `existsByRut`).
    *   Evita cargar listas masivas de datos en memoria, solucionando el problema de rendimiento anterior.

5.  **Entity (`@Entity`):** Es un reflejo simple y limpio de la tabla en la base de datos. **No contiene lógica de negocio ni validaciones complejas**. Su única responsabilidad es mapear los datos.

*   **Cuerpo de la Petición (Body - JSON):** El frontend debe enviar un objeto JSON que coincida con la estructura de `UsuarioRegistroDTO`.
