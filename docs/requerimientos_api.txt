## **Fase 1: Gestión de Usuarios (Completada)**

### **Endpoint de Registro de Usuario**
*   **URL:** `/api/usuarios/register`
*   **Método:** `POST`
*   **Descripción:** Registra un nuevo usuario.
*   **Cuerpo de la Petición (JSON):** `UsuarioRegistroDTO`
*   **Respuestas Posibles:**
    *   `201 CREATED`: Usuario creado exitosamente.
    *   `400 BAD REQUEST`: Datos de entrada inválidos (RUT, email, etc.).
    *   `409 CONFLICT`: El RUT o el email ya existen.

### **Endpoint de Login de Usuario**
*   **URL:** `/api/usuarios/login`
*   **Método:** `POST`
*   **Descripción:** Autentica a un usuario con su email y contraseña.
*   **Cuerpo de la Petición (JSON):** `UsuarioLoginDTO`
*   **Respuestas Posibles:**
    *   `200 OK`: Autenticación correcta. Devuelve el objeto `Usuario` (sin contraseña).
    *   `401 UNAUTHORIZED`: Credenciales inválidas.

## **Fase 2: Plan de Acción - Migración de Movimientos (Pendiente)**

**Objetivo:** Migrar toda la lógica de ingresos y gastos, actualmente gestionada por `DatabaseHelper.kt`
en la app, para que sea manejada por el backend.
Esto centralizará los datos y permitirá la persistencia entre dispositivos.

### **Tareas Pendientes (Backend)**

1.  **Crear Entidad `Movimiento`:**
    *   **Propósito:** Reflejará la tabla de movimientos en la base de datos.
    *   **Campos sugeridos:** `id` (PK), `descripcion` (String), `monto` (double), `tipo` (Enum: `INGRESO`, `GASTO`), `fecha` (Date), y una relación `ManyToOne` con la entidad `Usuario`.

2.  **Crear DTOs para Movimientos:**
    *   `MovimientoRegistroDTO`: Para recibir la información de un nuevo movimiento desde la app.
    *   `MovimientoResponseDTO`: Para enviar la información de los movimientos a la app.

3.  **Crear `MovimientoRepository`:** Interfaz de Spring Data JPA para interactuar con la tabla de movimientos.

4.  **Crear `MovimientoService`:**
    *   **Lógica de Negocio:** Implementar métodos para registrar un nuevo movimiento, obtener todos los movimientos de un usuario y calcular el saldo actual.

5.  **Crear `MovimientoController`:** Exponer los nuevos endpoints REST.
    *   `POST /api/movimientos`: Para registrar un nuevo ingreso o gasto. Recibirá un `MovimientoRegistroDTO`.
    *   `GET /api/movimientos/{usuarioId}`: Para obtener el historial de todos los movimientos de un usuario específico.
    *   `GET /api/saldos/{usuarioId}`: Para obtener una vista consolidada del saldo actual del usuario.

### **Tareas Pendientes (Android)**

1.  **Actualizar `ApiService.kt`:** Añadir las nuevas funciones para los endpoints de `/movimientos` y `/saldos`.

2.  **Crear los DTOs de Movimiento:** Crear las `data class` correspondientes en el paquete `model.dto`.

3.  **Refactorizar `DashboardViewModel` (o similar):**
    *   Reemplazar todas las llamadas a `DatabaseHelper` (ej: `insertarSaldo`, `obtenerSaldosPorUsuario`) por llamadas a los nuevos endpoints de la API a través de `RetrofitClient`.

4.  **Refactorizar `DashboardScreen.kt`:**
    *   Asegurar que la UI consuma los datos del `ViewModel` que ahora provienen del backend.
    *   El formulario para añadir ingresos/gastos deberá invocar la nueva función del `ViewModel` que llama a la API.

5.  **Limpieza de Código:** Una vez que toda la lógica esté migrada y probada, eliminar los métodos obsoletos de `DatabaseHelper.kt` para completar la migración.
